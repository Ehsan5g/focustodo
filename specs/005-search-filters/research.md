# Research & Decisions: Task Search & Filters (F005)

**Feature**: `005-search-filters` | **Date**: 2026-09-17
**Sources of truth**: [spec.md](spec.md) (FR-001–FR-015, 12 edge cases, Assumptions), [../003-task-management/research.md](../003-task-management/research.md) (D4 read architecture, D9 action results), [../004-task-categories/research.md](../004-task-categories/research.md) (D4 resolution pattern, D6 index evaluation, D11 zero-deps), constitution II ("task filters" shared schema) + technology constraints
**NEEDS CLARIFICATION items**: none — the spec's clarify session closed with the submit-only search decision; everything below resolves implementation-design questions the constitution routes to the plan.

## D1: List architecture — client-owned criteria + one five-step read action

- **Decision**: `/` stays a Server Component that renders the DEFAULT view (all of the user's tasks, newest first) plus the user's category options — the initial data for a client `TaskListContainer` that owns the criteria state (search, status, priority, categoryId, due-date preset, sort). Every criteria change — and every task-mutation success — re-reads through ONE new server action: `fetchTasks(criteria)` in `src/server/actions/task-filter-actions.ts`, five steps, returning `{ status: "success"; tasks: TaskDto[]; total: number }`. The F003 read service in `src/server/tasks/service.ts` is extended to take the built criteria; the criteria→where/orderBy mapping is a separate pure module (D3). Criteria are session-only view settings — never in the URL, never persisted (spec Assumptions).
- **Rationale**: the user-mandated constraint requires every search/filter/sort request to ride a five-step action returning stable serializable data; constitution III keeps the page server-rendered by default and Prisma out of the client; one read path keeps the ownership predicate (constitution I) auditable in exactly one place. `total` is the length of the returned array — the list is unpaginated (the spec defines no pagination), so a second COUNT query would be pure overhead.
- **Alternatives considered**: (a) URL searchParams + server re-render per change — rejected: the spec's Assumptions exclude address reflection, and a full round trip would re-render the whole page on every submit; (b) a client data library (TanStack Query/SWR) — rejected: a new dependency for what one action + `useState` covers (constitution: no unnecessary libraries); (c) `router.refresh()` with criteria in cookies — rejected: cookies persist across sessions, violating the session-only assumption.

## D2: The shared filter schema — `taskFilterSchema`, one normalization rule

- **Decision**: `src/validation/task-filter-schema.ts` exports `taskFilterSchema` — the constitution's "task filters" shared schema: optional `search` (trimmed; 1–200 characters after trim; whitespace-only or absent ⇒ no search criterion), optional `status` (`TODO|IN_PROGRESS|COMPLETED`), optional `priority` (`LOW|MEDIUM|HIGH`), optional `categoryId` (non-empty string), optional `dueDate` preset (`OVERDUE|DUE_TODAY|DUE_THIS_WEEK|NO_DUE_DATE`), and `sort` (`NEWEST_FIRST|OLDEST_FIRST|DUE_EARLIEST|PRIORITY_HIGH_LOW|TITLE_A_Z`, default `NEWEST_FIRST`). An absent optional field means "All". Normalization (trim + whitespace→none) lives ONLY here, exactly as `nameKey` derivation lives only in the category service (F004 D1).
- **Rationale**: constitution II names task filters among the schemas that MUST be shared between client and server; enums make impossible criteria unrepresentable; the 200-character input bound is an input-sanity limit (FR-012's "malformed or impossible requests fail safely"), not a data constraint — nothing longer is a useful query against 120-character titles and it keeps the LIKE pattern bounded; one normalization rule prevents client/server divergence.
- **Alternatives considered**: (a) "ALL" sentinels inside every enum — rejected: they widen the contract with non-data values the server must special-case; absence already means All; (b) free-form status/priority strings coerced later — rejected: constitution II makes the enums the contract; (c) client-side-only normalization with raw passthrough — rejected: the server is authoritative (constitution I).

## D3: Matching, windows, sorting — pure query builder, escaped insensitive contains, UTC calendar-day windows

- **Decision**: `src/server/tasks/task-query.ts` is a pure module (no Prisma client, no React) exporting `buildTaskQuery(criteria, now)` → `{ where, orderBy }`. Search becomes the `OR` of title/description `contains` with `mode: "insensitive"`, and the token is LIKE-escaped first (`\` → `\\`, `%` → `\%`, `_` → `\_`) so every character matches literally. Status/priority/category map to equality only when present. Due presets derive from `now` in UTC calendar days (dueDate is stored as a UTC-midnight calendar day — F003 contract): `OVERDUE` = `dueDate < today` AND `status != COMPLETED` (identical semantics to F003's `isOverdue` — one definition, locked by a unit test); `DUE_TODAY` = `[today, today+1)`; `DUE_THIS_WEEK` = `[today, today+7)` — "today through the next 7 days including today" (spec Assumptions); `NO_DUE_DATE` = `dueDate: null`. Sorting: `NEWEST_FIRST` = `createdAt desc`; `OLDEST_FIRST` = `createdAt asc`; `DUE_EARLIEST` = `dueDate asc` with nulls last, then `createdAt desc`; `PRIORITY_HIGH_LOW` = `priority desc` (Postgres enum order LOW→HIGH, pinned by the F003 schema declaration) then `createdAt desc`; `TITLE_A_Z` = `title asc` then `createdAt desc` — FR-007's newest-first tie-break appended to every non-createdAt sort.
- **Rationale**: pure and unit-tested (constitution IV); one place for overdue/window semantics prevents drift from `rules.ts`; escaping is what makes `%`, `_`, quotes, and emoji match literally (spec edge case) and keeps user input out of pattern semantics without raw SQL (constitution I: Prisma APIs only); UTC matches F003's storage convention so "today" is computed once at the action boundary.
- **Alternatives considered**: (a) Postgres full-text (`tsvector`) — rejected: a migration + index for a need this scale does not have (D6); (b) raw `ilike` fragments — rejected: bypasses Prisma's parameterization; (c) storing an `isOverdue` flag — rejected: F003 invariant — derived, never stored.

## D4: Category criterion — owner-resolved before the query, indistinguishable rejection

- **Decision**: when `categoryId` is present, the service resolves it via `category.findFirst({ where: { id: categoryId, userId } })` BEFORE building the task query; a miss (foreign, unknown, or just-deleted) returns `validation_error` with the `categoryId` field error — the same message F004's assignment path uses — and nothing queries. The client then drops the stale criterion, refetches once, and the options list (re-read after mutations) no longer offers the deleted category (FR-013 edge case: "the category disappears from the filter options and the list stops filtering by it, applying the remaining criteria without errors").
- **Rationale**: reads must obey the same ownership boundary as writes — a foreign id is rejected for the same reason F004 rejects it on assignment (constitution I covers metadata too); the self-healing drop is what makes a category deleted in another tab/surface vanish from the filter without a crash or a misleading "no tasks match".
- **Alternatives considered**: (a) putting `categoryId` straight into the task `where` — results would still be user-scoped, but a stale/deleted filter would silently show an empty list and never heal; rejected on UX correctness, not just security; (b) resolving by id alone then checking `userId` — rejected: a two-step existence-leak pattern; the compound predicate is one query and one answer.

## D5: Client state & interactivity — submit-only search, one request per change, refetch on mutations

- **Decision**: `TaskListContainer` (client) holds the criteria in `useState`; `TaskFiltersBar` presents the controls. Search submits ONLY via form submit (Enter or the explicit search control) — no onChange narrowing, no debounce (the clarified 2026-09-17 decision); every criteria change triggers exactly one `fetchTasks`; a pending indicator covers the in-flight read. FR-013 freshness: the container wraps the whole list surface, so the mutation flows (the create/edit control, `TaskItem` complete/reopen/delete) call it back through an optional `onSettled` callback prop; the container re-queries with the ACTIVE criteria after every mutation result. A full reload resets everything to defaults (session-only state — spec edge case).
- **Rationale**: the clarification removed all timing waits (deterministic tests, immediate UI response); React capabilities suffice (constitution III: no new libraries); the callback path is the same mechanism F003 already uses to hand mutation results to the page — no event bus, no global store.
- **Alternatives considered**: (a) debounce — explicitly rejected by the clarification; (b) TanStack Query for revalidation — new dependency (D9); (c) relying on `revalidatePath()` alone — insufficient: it refreshes the server render, but the container owns the rendered list after mount and must refetch itself.

## D6: Index evaluation — evaluate, defer, and record revisit triggers (constitution III)

- **Decision**: F005 queries always anchor on `userId` (base predicate) with equality filters on `status`/`priority`/`categoryId`, a range/null filter on `dueDate`, and insensitive `contains` on `title`/`description`. At the constitution's operating scale (≤ hundreds of tasks per user), the F003 default `@@index([userId, createdAt(sort: Desc)])` plus a base-table filter scan is sufficient; full-text/trigram indexes are not justified yet. RECORDED, not built: (1) if per-user task counts reach ~10k or filter latency exceeds SC-001/SC-002 (2 s), add the spec-named per-user indexes — `@@index([userId, status])`, `@@index([userId, priority])`, `@@index([userId, dueDate])` (the `[userId, categoryId]` case already exists from F004) or one compound `[userId, status, priority, dueDate]` per the then-dominant pattern; (2) if search latency regresses at scale, add a `pg_trgm` GIN index on `title`/`description`. Revisit at each feature's plan gate.
- **Rationale**: indexes MUST be evaluated (constitution III) — evaluation with recorded revisit triggers is the YAGNI-compliant answer; premature compound indexes on unproven patterns violate "no premature design"; F004's D6 deferred exactly these indexes and this is the follow-through.
- **Alternatives considered**: (a) building all five spec-named indexes now — rejected: speculative (F004's D6 deferred them for the same reason); (b) skipping evaluation — rejected: a constitution mandate.

## D7: UI surface — native controls in established conventions; zero new dependencies

- **Decision**: the filter bar is a labeled search form (input + explicit submit control, Enter submits), selects for status/priority/category/due-date/sort in the established Tailwind + shadcn/ui conventions, a "Reset filters" control visible while any criterion is active, the count line, and a no-match empty state with its own reset. Native `<form>`/`<select>`/`<input>` elements; no combobox or command-menu library. Category options come from the page's category projection — the same `{ id, name }` shape the F004 picker already reads (alphabetically by `nameKey`).
- **Rationale**: constitution III/V + the "no unnecessary libraries" technology constraint; selects match the F003 priority picker and F004 category picker patterns; the bar stacks vertically at 320 px with no horizontal scrolling (SC-006).
- **Alternatives considered**: (a) a Command/combobox component for search suggestions — rejected: no search history/suggestions by Assumptions; (b) custom dropdown reimplementation — cost without benefit; (c) arbitrary date-range pickers — rejected: FR-005 presets are fixed windows, not ranges.

## D8: Test strategy — the FR-015 map, failing-first

- **Decision**: FR-015's four layers map onto the existing stacks. Unit (Vitest): `taskFilterSchema` boundaries (enums; search trim/whitespace→none; 200-character bound; sort default), `buildTaskQuery` (escape table, OR matching incl. description-only hits, overdue boundary incl. the completed-tomorrow case, today/week window boundaries, no-due-date, all five sorts with nulls-last + newest-first tie-breaks, all criteria combined), and the criteria-aware service read with mocked Prisma + `requireSession` (ownership base predicate, forged/foreign `categoryId` → `validation_error` before any task query, count accuracy). Component (Vitest + Testing Library): `TaskFiltersBar` (typing does NOT fire requests; Enter and the submit control do; selects fire immediately; reset restores defaults) and `TaskListContainer` (count-line visibility rule, no-match empty state + its reset, pending state, stale-category drop). E2E (Playwright): US1–US5 journeys — search/filter/sort/reset/combination, FR-013 mutations-while-filtered (a created matching task appears; completing/deleting a matching task updates the view; completing turns an overdue task non-overdue), the stale-category edge case, reload-returns-defaults, User A/User B security (SC-003), and the 100-task scale + responsive walk (SC-006) — all deterministic waits on UI state, no sleeps.
- **Rationale**: FR-015 names all four layers and the search/filter coverage F003/F004 deferred lands here; F003/F004 patterns (mocked-Prisma service tests, RTL component tests, Playwright journeys) extend directly; submit-only search makes timing-free E2E possible.
- **Alternatives considered**: (a) E2E-only coverage — rejected: FR-015 requires unit coverage of matching/filtering/sorting incl. the overdue definition and tie-breaking; (b) visual-regression tooling — out of scope, no new tooling (D9).

## D9: No schema change, no new env, no new dependencies — a read-only substrate

- **Decision**: zero Prisma schema changes and zero migrations (criteria are code, not data); no new environment variables; no new runtime dependencies (native controls, testing stack unchanged). F005's additions are exactly the files in plan.md's project structure; everything else extends F003/F004 in place.
- **Rationale**: the feature is read-path logic over the existing `Task`/`Category` tables (spec Key Entities: Task unchanged; view settings are not data — spec Assumptions); constitution III (YAGNI) + the technology constraint; F004's D11 set the zero-deps precedent.
- **Alternatives considered**: (a) persisting view settings (new column/table) — rejected: session-only by Assumptions; (b) full-text columns/indexes — rejected: D6.

## Open questions

None — every decision is closed; the spec's one clarification (submit-only search) is absorbed into D2/D5.
